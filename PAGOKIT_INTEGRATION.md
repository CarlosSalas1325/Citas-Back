# PagoKit Integration

Generated by PagoKit on 2026-08-16.

Este documento describe la integración de **facturación de plataforma**: los negocios
(clínicas, salones, etc.) que usan este backend pagan una **suscripción mensual a la
plataforma** vía Stripe. Esto es independiente de cualquier cobro futuro que un negocio
le haga a sus propios pacientes/clientes por citas — ese flujo no fue tocado.

## Configuración

- Proveedor: Stripe (API version `2025-02-24.acacia`)
- SDK: `stripe@^17.5.0` (instalado: `17.7.0`)
- Stack: NestJS 11 + Express (Nest's default HTTP adapter)
- ORM: ninguno — Knex query builder directo, migraciones en `/migrations`
- Deploy target: Railway
- Billing mode: subscription (negocio → plataforma)
- Frontend style: hosted (Stripe Checkout / Billing Portal — este repo es solo backend)

## Por qué `req.rawBody` en vez de `express.raw()` manual

Este proyecto usa NestJS (no Express puro). En vez de desactivar el body parser global y
registrar `express.raw()` manualmente por ruta (patrón típico en Express puro), se usó el
mecanismo nativo de Nest: `NestFactory.create(AppModule, { rawBody: true })` +
`app.useBodyParser('json', { limit: '256kb' })`. Esto adjunta los bytes crudos exactos en
`req.rawBody` (Buffer) en cada request, sin afectar el parsing normal de `req.body` para el
resto de la API. El webhook verifica la firma contra `req.rawBody`, nunca contra `req.body`.

|---|---|---|---|

| POST | `/billing/cancel` | ADMIN, SUPER_ADMIN | Cancela la suscripción del negocio |

## Webhook events handled

- ✅ `customer.subscription.created` — upsert en `pagokit_subscriptions`
- ✅ `customer.subscription.updated` — upsert en `pagokit_subscriptions`
- ✅ `customer.subscription.deleted` — marca `status: canceled`
- ✅ `invoice.payment_failed` — log para dunning (Stripe Smart Retries maneja los reintentos)
- ⏳ `invoice.payment_succeeded` — TODO: reactivar acceso si estaba suspendido, en
  `src/modules/billing/webhook/stripe-webhook.controller.ts` (case `invoice.payment_succeeded`)
- ⏳ `payment_intent.succeeded` / `payment_intent.payment_failed` — logueados solamente; esta
  integración es 100% suscripción, no hay cobros únicos en este flujo
- ⏳ `charge.refunded` — confirmado por log; el trigger real es `POST /billing/refund`
- ⏳ `charge.dispute.created` — TODO: alertar a operaciones. Stripe da ~7 días para enviar
  evidencia vía `stripe.disputes.update()` antes de perder la disputa automáticamente

## Tablas agregadas al esquema

- `pagokit_stripe_customers` — 1 fila por `business_id`, mapea a `stripe_customer_id`
- `pagokit_subscriptions` — historial/estado de suscripciones por negocio
- `pagokit_idempotency_keys` — dedup de reintentos del lado del comercio (Rule 4)
- `pagokit_webhook_events_processed` — dedup de eventos de webhook por `event_id` (Rule 9)

Se usó el prefijo `pagokit_` para no chocar con ninguna tabla futura de "suscripciones" a
nivel de negocio (ej. si algún día un salón vende membresías a sus propios clientes).

## Ejemplo mínimo de frontend (hosted checkout)

Este repo es backend-only, así que no se generó ningún componente de UI. El flujo esperado
desde cualquier frontend (o `curl`) es:

```bash
# 1. El admin del negocio inicia sesión y obtiene un JWT (endpoint existente /auth/login)

# 2. Crea la sesión de checkout
curl -X POST https://<tu-backend>/billing/checkout \
  -H "Authorization: Bearer $JWT" \
  -H "Content-Type: application/json" \
  -d '{"email": "billing@minegocio.com"}'
# => { "url": "https://checkout.stripe.com/c/pay/..." }
# Redirige al usuario a esa URL. Stripe maneja el formulario de tarjeta — tu backend nunca
# ve el número de tarjeta (Rule 12).

# 3. Para administrar/cancelar la suscripción:
curl -X POST https://<tu-backend>/billing/portal \
  -H "Authorization: Bearer $JWT"
# => { "url": "https://billing.stripe.com/session/..." }
```

## Aviso legal — regulación regional (Rule 11)

El negocio operador de la plataforma está en **México (seller_country: MX)**, con
comercios/usuarios en MX, CO, AR, CL, PE y otros países de LATAM. Esta integración solo
recolecta el email de facturación del negocio (mínimo necesario para que Stripe entregue
recibos/facturas) — no se recolecta fecha de nacimiento, identificación oficial ni otros
datos demográficos.

- **México**: revisa la LFPDPPP (Ley Federal de Protección de Datos Personales en Posesión
  de los Particulares) para el aviso de privacidad. Si necesitas facturación fiscal formal
  (no solo el recibo de Stripe), Stripe **no es Merchant of Record** para este modelo de
  suscripción B2B, por lo que probablemente necesites emitir **CFDI 4.0** por tu cuenta.
- **Colombia, Argentina, Chile, Perú**: revisa la ley de protección de datos personales
  local de cada país donde tengas negocios registrados como clientes de la plataforma.
- Si en el futuro agregas cobros a consumidores finales (pacientes) en vez de solo a
  negocios, vuelve a evaluar la regulación aplicable — este documento cubre únicamente el
  cobro B2B de la plataforma a los negocios.
